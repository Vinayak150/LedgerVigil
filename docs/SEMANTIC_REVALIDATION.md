# RG-03 native semantic revalidation

The user approved this policy on 6 November 2026: preserve approval only when fresh deterministic calculation proves the reviewed outcomes and policies unchanged; otherwise require a new review. Migration 0031 implements this for single native SANDBOX RecordSettlement proposals under the installed 0.3.0 simulator and exact policy registry. The isolated parent includes the separately approved RG-08 changes in provisional migration 0030. Neither package is installed in the shared app yet.

Every original simulation, revision, evidence exception and approval stays immutable. The original read set and snapshot are not rewritten. A new semantic_recheck row stores the fresh complete canonical bundle and outcome, hashes, original simulation identity, actor/session, action, proposal version and sequence. It is completed and audited atomically and becomes immutable. An unfinished record or missing audit refuses the whole transaction at commit. Row-level security is forced and app access is read-only; writes use bounded session-authorized definer functions.

Eligibility is deliberately narrow. The original freshness checks still run. Every changed ACCOUNT version must be accounted for by a database-produced balance_dependency_step; a configuration update or role-binding change leaves an uncovered version, so the proposal remains stale even if the account is later renamed back. This new provenance starts at migration time; older unclassified version changes remain conservative. Document/evidence versions, relevant period changes, role bindings, profile/currency and statement/payout/payment range changes remain hard invalidations. Existing account version triggers and original point-in-time artifacts remain intact.

Before an override, approval, execution or maker revalidation that needs refresh, the API takes the same nonblocking action-key lock, then user/membership/ordered-role/session locks and rechecks permission and contributor independence. It locks the proposal, ledger, counter, periods, bindings and accounts, then captures and evaluates the complete fresh snapshot in that transaction. Existing same-key receipts are not recalculated. Unchanged captures use a read-only fast check and the existing writer, retaining established concurrency behavior. The runtime cannot insert a lock proof or a result directly.

Equivalence is calculated separately in Python and SQL. All postings, document effects, monetary deltas, policy identifiers/versions/outcomes/explanation codes, policy evidence, non-balance policy facts, kernel check results and other outcome fields must match. The explicit exceptions are changing input/snapshot hash provenance, absolute before/after account balances, P-CLR-02's absolute clearing balance, and E-DUP-01's sequence/head trace and generated sequence labels. The complete unnormalized values remain in the evidence. P-CLR-02's outcome must match, and SQL independently checks its fresh absolute clearing fact and sign against authoritative projected balances minus the proposed payout. This is an economic-equivalence decision, not a claim that every displayed balance fact stayed identical.

The installed simulator and policy versions must match the original exactly. Missing versions refuse refresh with 409; inconsistent projections refuse and roll back. A changed fresh result produces STALE through the owning action where supported, preserving prior decisions and releasing reservations through the existing state transition. An override's stale refusal still requires maker revalidation, as before. Any integrity defect rolls the entire action back. Existing production/provider/BOOKS gates remain unchanged.

Freshness reports reference semantic_recheck_id and original_pinned_seq while pinned_seq and observed_seq identify the fresh approved-equivalent capture used by the action. Original proposal read_set and simulation APIs still show their historical values. Allowed APPROVE/EXECUTE actions can mean a permitted attempt requiring semantic calculation, not a promise of a successful verdict.

Proof packs include completed rechecks no later than the pack's captured version and creation time, so later actions do not contaminate an earlier pack. Packs with rechecks display them and anchor the newest included financial prefix. Packs without rechecks preserve their previous serialization. Native diagnostic JSON exports with rechecks use ledgervigil.native-execution-proof/2; existing /1 exports remain valid. The standalone verifier checks both original and fresh capture hashes/sequence heads and requires the successful recheck referenced by the execution report. Neither verifier establishes external authenticity or accounting accuracy.

The established Q-16/X2 trust boundaries remain: the application is trusted to capture and evaluate inputs, and the worker serializes exports. Database binding, independent comparisons and authoritative clearing checks strengthen this path but do not make a compromised application or worker untrusted. Local Git is not offsite storage or a signature. Accounting stays UNREVIEWED. AI detection remains Claude's separate work.

Migration numbering is provisional and must be reconciled with Claude before integration. Downgrade refuses when any tenant has recheck history, preserving evidence. Exact empty-schema round-trip checks use a fresh database rather than deleting historical evidence.
